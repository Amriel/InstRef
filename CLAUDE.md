# Правила роботи над InstRef

Читається автоматично на початку роботи в цій теці. Це робоча угода, а не опис
проєкту — опис у `DEVELOPMENT.md`, інструкція користувача в `README.md`.

---

## Головне правило: DEVELOPMENT.md оновлюється завжди

**Будь-яка зміна коду завершується оновленням `DEVELOPMENT.md`.** Не «за
потреби», не «як буде час» — у тій самій відповіді, що й сама зміна. Документ
описує застосунок таким, яким він є ЗАРАЗ; розбіжність між ними гірша за
відсутність документа, бо їй вірять.

Що саме оновлювати — залежить від того, що зробив:

| Зробив | Онови в DEVELOPMENT.md |
|---|---|
| Нову можливість | розділ, якого вона стосується + рядок у таблиці версій |
| Виправив баг | **рядок у «Журналі помилок»**: симптом → корінь → урок |
| Новий модуль чи файл | «Карту модулів» |
| Нову таблицю чи стовпець | розділ «База даних» + опис міграції |
| Змінив потік роботи | схему у відповідному розділі |
| Додав поле конфігу | цифру «полів конфігу» в шапці |
| Змінив словник тегів | цифри категорій/тегів/синонімів |
| Підняв версію | таблицю версій і шапку |

**Журнал помилок — найцінніша частина документа.** Кожен виправлений баг
дописується туди трьома частинами: як це виглядало для користувача, у чому
була справжня причина, і який урок з цього на майбутнє. Без урока рядок
марний.

Числа в документі мають бути справжніми. Перед відправкою — звірити:

```bash
python - <<'PY'
import sys; sys.path.insert(0, '.')
from dataclasses import fields
from igsaved.config import Config
from igsaved.taxonomy import Taxonomy
tax = Taxonomy()
print("полів конфігу:", len(fields(Config)))
print("категорій:", len(tax.categories), "тегів:", len(set(tax.all_tags())),
      "синонімів:", len(tax.aliases), "груп несумісних:", len(tax.exclusive))
PY
python -m pytest tests/ -q | tail -1        # кількість тестів у шапку
```

## Порядок дій на кожну зміну

1. **Спершу дані, потім здогади.** Якщо користувач описує проблему —
   подивитись у його `state.db`, логи, конфіг. Половина «очевидних» причин у
   цьому проєкті виявлялась хибною. Копіювати базу разом із `-wal` і `-shm`,
   інакше читаєш застарілий знімок.
2. Написати код. Коментарі — українською, пояснюють **чому**, а не що.
3. Тест на кожну виправлену помилку. У докстрінгу — симптом, який він охороняє.
4. `python -m pytest tests/ -q; echo $?` і `ruff check igsaved tests` — має бути
   зелено **і код виходу 0**: Qt уміє впасти вже після «passed».
5. GUI перевіряється тестами `tests/test_ui.py` (offscreen); нову кнопку чи
   поле — туди ж, а не в разовий скрипт у /tmp.
6. **Оновити `DEVELOPMENT.md`.**
7. Підняти версію в `igsaved/__init__.py` **і дописати розділ у `CHANGELOG.md`**
   (англійською, для людини, не для розробника): саме він стає нотатками
   релізу на GitHub і текстом у «Про застосунок → Оновлення».
8. Оновити `README.md`, якщо змінилось видиме користувачу.
9. Зібрати й доставити.

## Принципи, від яких не відступаємо

**Жодних тихих відмов.** Кожна гілка, що веде до «нічого не робимо», має
сказати чому: `self.log(...)`, банер, рядок у журналі. Це не ввічливість — це
головне джерело болю в цьому проєкті. Порожній результат при цьому **не
зберігається**: порожній опис колись виглядав як «вже описано» й назавжди
блокував повторну спробу.

**Один ключ на всю систему.** Майже кожен баг тут — це дві частини коду, які
по-різному розуміють одне поняття. Ключ підбірки (`pk`, ніколи не назва),
статус файлу, тип медіа, порожній результат. Назва — для людини, `pk` — для
коду.

**Правила застосовуються, а не проголошуються.** Словник тегів не просять
дотримувати — його перевіряють кодом після відповіді моделі. Те саме з будь-
якою домовленістю, яку може порушити зовнішня система.

**Нічого не видаляти без прямої згоди.** Файли, елементи Eagle, чергу ревʼю —
тільки після окремого підтвердження, і краще в кошик, ніж назавжди.

## Технічні дрібниці, на яких уже спіткнулись

* `.bat` **мусять** мати CRLF — інакше Windows їх не виконає. У репозиторії це
  гарантує `.gitattributes`; при доставці через zip — конвертувати руками.
* У репозиторії на змонтованій теці — `git config core.fileMode false`, інакше
  git вважає зміненими всі файли (монтування віддає їх як 0700).
* **Git на змонтованій теці лишає стійкий `index.lock`**: git створює його і не
  може видалити (монтування забороняє unlink) — наступна git-команда
  користувача падає з «Another git process seems to be running». Тому git-
  операції робити в контейнерній копії, а на диску користувача — уникати;
  якщо довелось, останнім кроком `mv .git/index.lock _to_delete/` і без
  жодного git після цього.
* Змонтована тека користувача забороняє видалення: розпаковувати в `/tmp`,
  потім `cat` поверх файлів. `unzip -o` напряму не працює.
* **Доставка переписує `.git/config` — remote має бути і в контейнерній
  копії.** Одного разу `origin` зник після доставки, і `git push` упав із
  «'origin' does not appear to be a git repository». У контейнері:
  `git remote add origin https://github.com/Amriel/InstRef.git`.
* **Понад три теги одним push — GitHub не запускає workflow.** Так задумано
  на їхньому боці. Тег для релізу пушити окремо: `git push origin vX.Y.Z`;
  якщо вже поїхав пачкою — видалити (`git push origin :refs/tags/vX.Y.Z`)
  і запушити знову.
* **Перед перезаписом `.git` на диску користувача — звірити HEAD.** Доставка
  переписує `.git` з контейнерної копії; власний коміт користувача вона затре
  мовчки. Тому спершу `cat .git/refs/heads/main` на диску: він має дорівнювати
  батьківському коміту того, що везеш. Розбіжність — стоп і звірка, а не
  перезапис.
* `config.json`, `session.json`, `state.db` і `taxonomy.json` — робочі файли
  користувача. Вони в `.gitignore` і не мають потрапляти в жоден архів чи
  коміт: у `session.json` лежить cookie, що дає повний доступ до акаунта.
* Порожнє значення в конфізі = «взяти вбудоване». Так оновлення покращує
  типове тим, хто його не чіпав, і не затирає чужу правку
  (`vision_prompt`, `LEGACY_TEMPLATES`).
* `CREATE TABLE IF NOT EXISTS` не змінює наявну таблицю. Нові стовпці —
  `ALTER TABLE`; змінений первинний ключ — перезбирання таблиці.
* Міграцію перевіряти на копії реальної бази до відправки, а не лише на порожній.
* `sync.py` не знає про Qt і не має дізнатись: той самий двигун працює в `cli.py`.
* Винятки instagrapi впізнаються за **текстом** (`instagram.classify_error`),
  а не за класами: бібліотека їх перейменовує між версіями.
* Свідомий пропуск проходу (кулдаун, замок) — це `Stats.reason`, а не
  помилка: інакше планувальник щоразу показує вікно «з помилками».
* Залежності запінені точно. Піднімати версію — окремим комітом після
  прогону суїту у **чистому** venv (`python -m venv /tmp/v && pip install -r
  requirements.txt && pip check`): середовище, де щось уже стояло, ховає
  конфлікти.

## Реліз

Збірка .exe можлива лише у Windows, тому її робить GitHub Actions:

```bash
# після того, як версію піднято і DEVELOPMENT.md оновлено
git add -A && git commit -m "..."
git tag -a vX.Y.Z -m "InstRef X.Y.Z" && git push origin main --tags
```

Тег `v*` запускає `release.yml`: тести → PyInstaller → Inno Setup →
інсталятор і портативний zip у реліз. Версія береться з
`igsaved/__init__.py`, тому піднімати її треба **до** тегу.
